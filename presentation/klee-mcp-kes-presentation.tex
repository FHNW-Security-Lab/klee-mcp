\begin{frame}{The LLM selects what to check}
  \begin{points}
    \item Read the code and identify a suspicious function
    \item Identify inputs that should vary during analysis
    \item Inspect callers and propose assumptions about valid inputs
    \item Submit a structured candidate to the verification tool
  \end{points}
  \vspace{3mm}
  \centering\input{figures/llm-role}
  \takeaway{The LLM supplies a hypothesis and context; execution must check it}
  \note{[1:00; cumulative 4:00] Introduce the responsibilities before naming the integration protocol. The LLM narrows the analysis to a candidate function, identifies its variable inputs, and looks at how other code calls it. It may infer assumptions incorrectly. In the running schematic example, the function processes records and a caller appears to pass at most four. This is an illustrative example, not an extra benchmark result.}

% 05 | 4:00--5:45
\begin{frame}{Symbolic execution checks possible executions}
  \begin{columns}[c,onlytextwidth]
    \column{0.46\textwidth}
    \begin{points}
      \item Use variables instead of one fixed test input
      \item Follow branches and collect their conditions
      \item Solve those conditions to find possible paths
      \item If a path fails, obtain a concrete input that reaches it
    \end{points}
    \column{0.50\textwidth}
    \centering\input{figures/symbolic-tree}
  \end{columns}
  \takeaway{KLEE is the symbolic execution engine used in our system}
  \note{[1:45; cumulative 5:45] Contrast an ordinary test, which picks one input, with symbolic execution, which reasons about sets of inputs using constraints. The schematic branch distinguishes processing at most four records from processing more. At a branch, KLEE explores each feasible alternative. The solver determines whether the conditions along a path can hold together. A feasible error path yields a concrete witness. This does not mean enumerating every integer separately. Many branches and loop iterations can still create a large number of execution states.}
\end{frame}

% 06 | 5:45--7:45
\begin{frame}{From the LLM candidate to a KLEE verdict}
  \centering\input{figures/harness-bridge}
  \vspace{2mm}
  \begin{points}
    \item \textbf{MCP} (Model Context Protocol) connects the LLM to the server
    \item A \textbf{harness} sets up symbolic inputs and calls the target function
    \item The server compiles harness + target to LLVM bitcode and runs KLEE
    \item The result returns to the LLM for interpretation and caller review
  \end{points}
  \note{[2:00; cumulative 7:45] Walk once through the complete integration. MCP is the tool interface, not the execution engine. The LLM submits structured data identifying the function, symbolic inputs, and proposed assumptions. The server translates these into a small driver program, the harness. It allocates input objects, makes selected values symbolic, adds assumptions, and calls the target. LLVM bitcode is the compiled representation KLEE executes. Linked library code includes functions called by the target; choosing a function-level entry does not restrict execution to its body. KLEE checks paths and supplies evidence. The server returns the verdict, diagnostics, and any concrete witness to the LLM. The LLM can explain the result or request caller investigation. The server also supports the optional retry introduced later. Transition: what exactly does each returned verdict establish?}
\end{frame}

\end{frame}

% 08 | 9:00--10:30
\begin{frame}{Where do we start symbolic execution?}
  \centering\input{figures/entry-vs-function}
  \vspace{2mm}
  \begin{points}
    \item \textbf{From an entry point}: preserve caller checks; often a larger search
    \item \textbf{Directly at the function}: focus the search, but lose caller guarantees
  \end{points}
  \takeaway{Our direct harness needs assumptions about the missing caller context}
  \note{[1:30; cumulative 10:30] Compare the two starting points before introducing caller contracts. From the top means a chosen application or public API entry, not necessarily main and not every function in a repository. Symbolic execution follows the selected entry's parsing, validation, and calls. A successful caller check contributes constraints to the path that reaches the target. A direct harness skips this prefix and supplies symbolic arguments to the target, so it can admit inputs a real caller would reject. Direct analysis still executes functions called by the target. It often avoids expensive prefix exploration, although neither starting point guarantees a cheaper or complete run. We use function-level harnesses and ask the LLM to propose relevant caller preconditions. These approximate selected guarantees; they do not reproduce the entire calling context or prove equivalence to entry-based analysis.}
\end{frame}

% 09 | 10:30--13:30
\begin{frame}{A caller contract is a promise about inputs}
  \centering\input{figures/contracts}
  \vspace{1mm}
  \begin{points}
    \item Model the promise in the harness: assume $0\leq n\leq4$
    \item Exclude $n>4$ paths; fewer loop iterations reduce the search
    \item A harness assumption adds no runtime check to the real function
  \end{points}
  \vspace{2mm}
  {\small
  \renewcommand{\arraystretch}{1.2}
  \begin{tabular}{@{}>{\raggedright\arraybackslash}p{40mm}>{\raggedright\arraybackslash}p{92mm}@{}}
    \textbf{libpng examples} & \textbf{Why caller context changes the interpretation}\\
    \midrule
    CVE-2015-8540 helper & Local error without the contract; infeasible with it\\
    \texttt{png\_format\_number} & Local error; all reviewed callers satisfy its precondition\\
  \end{tabular}\par}
  \takeaway{A local error need not be reachable through real callers}
  \note{[3:00; cumulative 13:30] Define the promise using the schematic records example: the harness has storage for 16 records, n is how many to process, and current callers pass at most four. The direct harness models that promise as 0 <= n <= 4. It excludes paths requiring n > 4 and limits a loop over n records to four iterations, usually reducing execution states, solver work, and memory. It also narrows the safety claim. An assumption in a harness does not add a runtime check to the function. The LLM may infer the contract from documentation or callers and can infer it incorrectly. The two libpng examples illustrate the consequence; they do not use the schematic four-record bound. In the CVE-2015-8540 case, the extracted helper reports an error in libpng 1.2.56, 1.6.19, and 1.6.47 without its caller contract; supplying the contract changes the verdict to infeasible. The historical fix was in callers, so a local error does not establish a newly reachable vulnerability in later versions. Separately, png\_format\_number relies on an unchecked internal precondition that every reviewed shipped call site satisfies. Reaching a function and reaching its error state are different questions. The reachability tool probes entry-to-function reachability; it does not automatically establish the same error under real calling context. Transition: those callers satisfy the contract today, but what if usage changes?}
\end{frame}

% 10 | 13:30--15:15
\begin{frame}{Why retry: what if the function is used differently?}
  \centering\input{figures/relax}
  \vspace{2mm}
  \begin{points}
    \item The LLM may have inferred a bound that is too restrictive
    \item A new caller or refactor may pass more records, such as $n=8$
    \item Retry at the same function, without the LLM bounds
  \end{points}
  \takeaway{A new error can reveal a fragile assumption, even if today's usage is safe}
  \note{[1:45; cumulative 15:15] A completed bounded run may show no error for today's usage. That leaves a second question: is the function robust if a future caller uses it differently? In our schematic example, eight records still fit in the 16-record object, but the execution was excluded by the four-record bound. The optional server retry removes the LLM bounds after an infeasible verdict; it still uses the same function-level harness and engine model. It does not restart from the application or API entry point. It may find an error, complete without one, or remain unresolved. Preserve both verdicts and the changed assumptions. An error outside the current contract does not imply a current reachable vulnerability: we must decide whether to enforce the contract, strengthen the function, or revise the assumption. The implementation retracts the declared LLM bounds; it does not prove which particular bound caused a changed result.}
\end{frame}
