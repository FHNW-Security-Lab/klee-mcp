\begin{frame}{The LLM selects what to check}
  \begin{points}
    \item Read the code and identify a suspicious function
    \item Identify inputs that should vary during analysis
    \item Inspect callers and propose assumptions about valid inputs
    \item Submit a structured candidate to the verification tool
  \end{points}
  \vspace{3mm}
  \centering\input{figures/llm-role}
  \takeaway{The LLM supplies a hypothesis and context; execution must check it}
  \note{[0:45; cumulative 3:30] Introduce the responsibilities before naming the integration protocol. The LLM narrows the analysis to a candidate function, identifies its variable inputs, and looks at how other code calls it. It may infer assumptions incorrectly. In the running schematic example, the function processes records and a caller appears to pass at most four. This is an illustrative example, not an extra benchmark result.}
\end{frame}

% 05 | 03:30--05:00
\begin{frame}{Symbolic execution checks possible executions}
  \begin{columns}[c,onlytextwidth]
    \column{0.46\textwidth}
    \begin{points}
      \item Use variables instead of one fixed test input
      \item Follow branches and collect their conditions
      \item Solve those conditions to find possible paths
      \item If a path fails, obtain a concrete input that reaches it
    \end{points}
    \column{0.50\textwidth}
    \centering\input{figures/symbolic-tree}
  \end{columns}
  \takeaway{KLEE is the symbolic execution engine used in our system}
  \note{[1:30; cumulative 5:00] Contrast an ordinary test, which picks one input, with symbolic execution, which reasons about sets of inputs using constraints. The schematic branch distinguishes processing at most four records from processing more. At a branch, KLEE explores each feasible alternative. The solver determines whether the conditions along a path can hold together. A feasible error path yields a concrete witness. This does not mean enumerating every integer separately. Many branches and loop iterations can still create a large number of execution states.}
\end{frame}

% 06 | 05:00--06:00
\begin{frame}{The bridge: a small program KLEE can execute}
  \centering\input{figures/harness-bridge}
  \vspace{3mm}
  \begin{points}
    \item A \textbf{harness} sets up inputs and calls the selected function
    \item The server turns declared inputs into symbolic variables
    \item Assumptions restrict those variables before the call
    \item The harness and target code are compiled to LLVM bitcode
  \end{points}
  \note{[1:00; cumulative 6:00] A language-model explanation is not directly executable. The structured candidate is translated into a small driver program: the harness. It allocates input objects, makes selected values symbolic, adds the declared assumptions, and calls the function. LLVM bitcode is the compiled representation KLEE executes. Library bitcode can be linked to include functions called by the target. Selecting one entry avoids starting analysis at every function in the repository; it does not mean only that one function's body executes.}
\end{frame}

% 07 | 06:00--07:15
\begin{frame}{How the LLM and KLEE work together}
  \centering\input{figures/pipeline}
  \vspace{3mm}
  \begin{points}
    \item \textbf{LLM}: choose the candidate, inputs, and assumptions
    \item \textbf{MCP server}: generate the harness and manage KLEE runs
    \item \textbf{KLEE}: return a verdict and execution evidence
    \item \textbf{LLM}: explain the result and investigate caller context
  \end{points}
  \note{[1:15; cumulative 7:15] MCP means Model Context Protocol: it is the tool interface, not the analysis engine. Walk through the arrows in order. The LLM submits structured data; the server builds the driver and runs KLEE; the result returns through the server to the LLM. The LLM can then request a reachability check or explain the finding. The server can also perform the optional retry discussed shortly. The loop separates proposing an input model from checking behavior within that model.}
\end{frame}

% 08 | 07:15--08:15
\begin{frame}{What the verdicts mean}
  \renewcommand{\arraystretch}{1.6}
  \begin{tabular}{@{}>{\raggedright\arraybackslash}p{29mm}>{\raggedright\arraybackslash}p{103mm}@{}}
    \textbf{Confirmed} & A matching error was found; a concrete input demonstrates it\\
    \textbf{Infeasible} & No matching error exists in the fully explored input model\\
    \textbf{Unresolved} & The run timed out, failed to build, or hit an engine error\\
  \end{tabular}
  \vspace{4mm}
  \begin{points}
    \item \textbf{Confirmed}: check whether real callers can supply that input
    \item \textbf{Infeasible}: ask which inputs the assumptions excluded
  \end{points}
  \note{[1:00; cumulative 8:15] Unresolved groups the literal statuses timeout, build\_failed, and klee\_error. A timeout is not a safety result. Infeasible requires completed exploration and a suitable model of the environment; unsupported behavior can weaken that interpretation. Most importantly, both confirmed and infeasible apply to the setup we supplied. Introduce the next question: did we execute the real caller or bypass it with a direct harness?}
\end{frame}

% 09 | 08:15--09:30
\begin{frame}{Where do we start symbolic execution?}
  \centering\input{figures/entry-vs-function}
  \vspace{2mm}
  \begin{points}
    \item \textbf{From an entry point}: preserve caller checks; often a larger search
    \item \textbf{Directly at the function}: focus the search, but lose caller guarantees
  \end{points}
  \takeaway{Our direct harness needs assumptions about the missing caller context}
  \note{[1:15; cumulative 9:30] Compare the two starting points before introducing caller contracts. From the top means a chosen application or public API entry, not necessarily main and not every function in a repository. Symbolic execution follows the selected entry's parsing, validation, and calls. A successful caller check contributes constraints to the path that reaches the target. A direct harness skips this prefix and supplies symbolic arguments to the target, so it can admit inputs a real caller would reject. Direct analysis still executes functions called by the target. It often avoids expensive prefix exploration, although neither starting point guarantees a cheaper or complete run. We use function-level harnesses and ask the LLM to propose relevant caller preconditions. These approximate selected guarantees; they do not reproduce the entire calling context or prove equivalence to entry-based analysis.}
\end{frame}

% 10 | 09:30--11:30
\begin{frame}{A caller contract is a promise about inputs}
  \centering\input{figures/contracts}
  \vspace{3mm}
  \begin{points}
    \item \textbf{Caller contract}: ``I will pass at most four records''
    \item A direct harness does not execute the caller that keeps this promise
    \item The LLM models this guarantee with the bound $0 \leq n \leq 4$
  \end{points}
  \takeaway{An assumption in the harness does not add a check to the real function}
  \note{[2:00; cumulative 11:30] Use this one schematic example consistently. The harness provides storage for 16 records; n says how many the function should process. Today's callers use at most four. An entry-based run can inherit that restriction from the executed caller code; a direct harness must model it explicitly. The LLM proposes n between zero and four as a description of that usage. KLEE therefore checks that usage, not every other way of calling the function. A caller contract can come from documentation or caller code. It may be a real requirement or an incorrect inference. Adding an assumption to the harness does not change the library or enforce the promise at runtime. Under n at most four, paths requiring n greater than four are excluded, and a loop over n records needs at most four iterations. This usually reduces execution states and solver work, while narrowing the claim to the allowed inputs.}
\end{frame}

% 11 | 11:30--13:00
\begin{frame}{Why retry: what if the function is used differently?}
  \centering\input{figures/relax}
  \vspace{2mm}
  \begin{points}
    \item The LLM may have inferred a bound that is too restrictive
    \item A new caller or refactor may pass more records, such as $n=8$
    \item Retry at the same function, without the LLM bounds
  \end{points}
  \takeaway{A new error can reveal a fragile assumption, even if today's usage is safe}
  \note{[1:30; cumulative 13:00] A completed bounded run may show no error for today's usage. That leaves a second question: is the function robust if a future caller uses it differently? In our schematic example, eight records still fit in the 16-record object, but the execution was excluded by the four-record bound. The optional server retry removes the LLM bounds after an infeasible verdict; it still uses the same function-level harness and engine model. It does not restart from the application or API entry point. It may find an error, complete without one, or remain unresolved. Preserve both verdicts and the changed assumptions. An error outside the current contract does not imply a current reachable vulnerability: we must decide whether to enforce the contract, strengthen the function, or revise the assumption. The implementation retracts the declared LLM bounds; it does not prove which particular bound caused a changed result.}
\end{frame}

    \item Use bounds to make that analysis tractable
    \item Retry to reveal behavior hidden by the assumptions
  \end{points}
